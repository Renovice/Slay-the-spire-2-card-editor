# cost-modifiers
Compared the card_editor mod's cost-modification engine against vanilla StS2's two-layer cost system (CardEnergyCost local modifiers + Hook.ModifyEnergyCostInCombat early/late global hooks; TemporaryCardCost + Hook.ModifyStarCost for stars).

Architecture: the mod is mostly well-integrated â€” intrinsic/aura discounts (CardCostsLess, CardTypeCostsLess) ride vanilla's global hook via Harmony postfixes on Hook.ModifyEnergyCostInCombat / Hook.ModifyStarCost plus matching postfixes on CardCostHelper's color helpers, so display number, cost color, playability and actual spend all read the same value. Created/drawn/generated-card energy discounts stamp real vanilla LocalCostModifiers (AddThisTurn/SetThisCombat/SetUntilPlayed with vanilla-consistent reduceOnly semantics and the vanilla Canonical<0 'Free' sentinel guard), so expiry follows vanilla EndOfTurnCleanup/AfterCardPlayedCleanup. X-cost cards correctly never receive energy discounts (vanilla early-returns before the hook), negative-cost sentinels are preserved, and 'free to play' uses vanilla SetToFreeThisTurn/ThisCombat.

Found 3 major divergences: (1) mod cost-INCREASE deltas are applied after vanilla's late hooks, so vanilla 'free' powers (Free Skill/Corruption/Void Form) get re-charged â€” inverting vanilla's free-always-wins ordering; (2) 'cost 1 more for N turns' on drawn/generated cards is normalized through the amount==-1 â‡’ Free shortcut and makes cards cost 0 (and cost-more amounts â‰¥2 silently last only 1 turn); (3) multi-turn drawn/generated discounts double-stamp on the first turn (2Ã— discount; half-cost becomes quarter-cost). Plus 4 minor ones: half-cost snapshots double-dip vanilla aura discounts; parallel star 'this turn' discounts outlive the turn (expire at next player-turn start, not turn end); card-type aura expiry/star auras don't fire cost-changed events (stale displayed costs on retained cards); and permanent over-reduction floors base at -1 (cost icon vanishes, card becomes immune to later cost increases) instead of vanilla's clamp at 0, also skipping vanilla's absolute-modifier clamping (Confused-set costs ignore the reduction). Known issues (ThisTurn round-granularity, count windows, etc.) were excluded.

## [major] Mod cost-increase effects re-charge cards that vanilla 'free' powers make free
VANILLA: Hook.ModifyEnergyCostInCombat runs early hooks first (cost increases like TangledPower use TryModifyEnergyCostInCombat) and 'free' effects last (FreeSkillPower/FreeAttackPower/CorruptionPower/VoidFormPower/BrilliantScarf all use TryModifyEnergyCostInCombatLate and set the cost to 0). Free therefore always wins over '+1 cost' debuffs.
MOD: The mod's CardCostsLess/CardTypeCostsLess adjustments run in a Harmony postfix on Hook.ModifyEnergyCostInCombat, i.e. AFTER vanilla late hooks. A negative delta ('cards cost 1 more') is applied as __result = Math.Max(0, __result - Delta), pushing a vanilla-freed card from 0 back up to 1. (The mod's own ForceFree is applied after its delta, so only vanilla free powers lose.)
SCENARIO: Player has a Free Skill charge (next Skill costs 0) while an editor effect 'your cards cost 1 more' is active. Vanilla rules: the skill is free and the charge is consumed. With the mod the skill displays and spends 1 energy â€” the 'free' buff visibly does nothing, yet its counter still decrements.
EVIDENCE: Mod: CardEditorCardCostsLessPatches.cs:36-55 (postfix subtracts combined.Delta after the original hook, Max(0, ...) re-adds cost on top of late-hook zero); signed negative deltas allowed per CardEditorExtraEffects.cs:6086-6091 and 32021-32023. Vanilla: Hook.cs:1245-1261 (early loop then late loop), TangledPower.cs:59-68 (increase = early hook), FreeSkillPower.cs:14-42 and CorruptionPower.cs:16 (free = late hook).

## [major] 'Drawn/generated cards cost 1 MORE for N turns' actually makes them cost 0
VANILLA: Vanilla cost-increase effects always add cost: TangledPower adds +Amount via the hook; FranticEscape/Modded use EnergyCost.AddThisCombat(+1). A cost increase can never zero a card's cost.
MOD: StampCostReductionForCard's Turns branch stamps AddThisTurn(+1) and then calls ApplyForTurns(card, -1, ...). ApplyForTurns runs NormalizeModifier(-1, Reduce) which converts amount -1 into CardExtraEffectCostModifier.Free, so it immediately calls ApplyZeroThisTurn â†’ EnergyCost.SetThisTurn(0) and schedules Free for the remaining turns. The absolute-0 modifier wins over the +1 relative one, so the card costs 0 for all N turns. Additionally, for cost-more amounts â‰¥ 2 with Turns duration, ApplyForTurns early-returns (amount <= 0 && != -1), so the increase silently applies only on the first turn and vanishes for the remaining turns.
SCENARIO: Configure 'drawn cards cost 1 more for 2 turns' and draw a 1-cost Strike: instead of costing 2, it costs 0 this turn and 0 again next turn. With 'cost 2 more for 3 turns', cards drawn on turns 2-3 of the window get no increase at all.
EVIDENCE: Mod: CardEditorDrawnGeneratedCostController.cs:473-486 (Turns branch passes isCostMore ? -amount into ApplyForTurns), CardEditorCreatedCardsCostPatches.cs:131-134 (NormalizeModifier turns Reduce/-1 into Free), 478-507 (ApplyForTurns normalizes then ApplyThisTurn immediately; line 479 early-return drops amounts <= 0 != -1), 392-411 + 260-269 (Free â†’ ApplyZeroThisTurn â†’ SetThisTurn(0)). Vanilla comparators: TangledPower.cs:66 (modifiedCost = originalCost + Amount), FranticEscape.cs:45 (AddThisCombat(1)).

## [major] Multi-turn drawn/generated discounts double-apply on the first turn (and quarter-cost for half)
VANILLA: A vanilla discount applies its amount exactly once per application: Pinpoint/Stomp do EnergyCost.AddThisTurn(-amount) a single time; there is no path that stacks the same discount twice from one trigger.
MOD: For duration=Turns, StampCostReductionForCard first stamps AddThisTurn(-N) itself, then calls ApplyForTurns(..., remaining + 1, ...) â€” and ApplyForTurns immediately calls ApplyThisTurn again, adding a second AddThisTurn(-N) the same turn. Result: 2N discount on the turn the card is drawn/generated, N on subsequent turns. The HalfCost variant is worse: it stamps SetThisTurn(half) and then ApplyForTurns â†’ TryApplyHalfCost recomputes from GetWithModifiers(All) (which already includes the half stamp) and stamps SetThisTurn(half/2) â€” quarter cost on turn 1.
SCENARIO: 'Drawn cards cost 1 less for 2 turns': draw a 3-cost card â€” it shows and spends 1 (3-2) on the draw turn instead of 2, then correctly 2 next turn. 'Drawn cards cost half for 2 turns' on a 4-cost card: costs 1 (quarter) on the draw turn instead of 2.
EVIDENCE: Mod: CardEditorDrawnGeneratedCostController.cs:473-486 (Reduce/Turns stamps AddThisTurn then calls ApplyForTurns with remaining+1), 436-445 (Half/Turns stamps SetThisTurn(half) then ApplyForTurns with HalfCost), CardEditorCreatedCardsCostPatches.cs:493 (ApplyForTurns applies ApplyThisTurn immediately before scheduling), 202-221 (TryApplyHalfCost reads GetWithModifiers(All) including the prior stamp). Vanilla: Pinpoint.cs:68 / Stomp.cs:78 (single AddThisTurn per trigger).

## [minor] Half-cost stamps bake live global discounts into an absolute local modifier, double-dipping vanilla auras
VANILLA: Vanilla absolute local cost modifiers are always fixed design numbers (Enlightenment sets 1, RocketPunch sets 0, ConfusedPower sets a rolled value); GetWithModifiers applies local modifiers FIRST and the global hook (powers/relics) afterwards, so aura discounts are never counted twice. The mod's own hook-based HalfCost (CardCostsLess modifier) also halves after all hooks, once.
MOD: TryApplyHalfCost / StampCostReductionForCard(HalfCost) compute the snapshot from GetWithModifiers(CostModifiers.All) â€” which includes vanilla power/relic discounts â€” and store half of that as an absolute SetThisTurn/SetThisCombat local modifier. The global hook then re-applies the same vanilla discount on top, so the aura is deducted twice; result also disagrees with the mod's hook-based half-cost.
SCENARIO: Vanilla Curious power active (Powers cost 2 less), a 4-cost Power token is created by 'created cards cost half this turn': snapshot = (4-2)/2 = 1, final cost = max(0, 1-2) = 0. The mod's own 'this card costs half' on the same card gives 1, and the natural reading (half of 4, minus 2) is 0/1 ambiguity resolved differently across the mod's two half-cost paths â€” the player sees inconsistent numbers.
EVIDENCE: Mod: CardEditorCreatedCardsCostPatches.cs:202-221 (GetWithModifiers(All) snapshot, vanilla hooks NOT suppressed â€” only editor hooks via SuppressCardEditorCostHooksScoped), CardEditorDrawnGeneratedCostController.cs:412-450; contrast hook path CardEditorCardCostsLessPatches.cs:52-55 (Floor(__result/2) after hooks, applied once). Vanilla: CardEnergyCost.cs:56-83 (locals before global hook â†’ hook re-applies), Enlightenment.cs:23-27 and CuriousPower.cs:12-33 (fixed absolute values vs separate hook discount).

## [minor] Star-cost 'this turn' discounts survive the enemy turn and next turn's start-of-turn triggers
VANILLA: Temporary star costs created with ClearsWhenTurnEnds (TemporaryCardCost.ThisTurn, used by SetToFreeThisTurn/SetStarCostThisTurn) are removed in CardModel.EndOfTurnCleanup, which runs at the end of the player turn (FlushPlayerHand) AND at the end of the enemy turn.
MOD: Created-cards star discounts use a parallel PendingStarDiscount list applied via the Hook.ModifyStarCost postfix; 'this turn' entries (RemainingTurns=1) are only decremented in OnAfterPlayerTurnStart, which runs as a postfix of Hook.AfterPlayerTurnStart on the NEXT player turn â€” after draw and after vanilla start-of-turn hooks. The discount is therefore still active for the whole enemy turn and during next-turn start-of-turn effects.
SCENARIO: 'Created cards' star cost is reduced by 2 this turn' applies to a star-cost token that is Retained. During the enemy turn the card still displays the discounted star cost, and a start-of-next-turn auto-play effect would spend the discounted star amount; a vanilla this-turn star discount would have lapsed at end of turn.
EVIDENCE: Mod: CardEditorCreatedCardsCostPatches.cs:107-118 + 176-182 (PendingStarDiscount with RemainingTurns), 665-710 (decrement only in OnAfterPlayerTurnStart), hooked at CardEditorMod.cs:2939-2958 (Hook.AfterPlayerTurnStart postfix); applied via CardEditorCardStarCostsLessPatches.cs:36-40. Vanilla: CardModel.cs:1306-1319 (EndOfTurnCleanup removes ClearsWhenTurnEnds star costs), CombatManager.cs:1036 and 1123 (cleanup at enemy-turn end and player-turn end).

## [minor] Card-type cost aura expiry and star auras never fire cost-changed events â€” stale displayed costs
VANILLA: When vanilla cost modifiers expire at end of turn, CardModel.EndOfTurnCleanup invokes EnergyCostChanged / StarCostChanged so NCard refreshes the printed cost immediately.
MOD: CardEditorCardTypeCostAuras.OnAfterPlayerTurnEnd removes expired ThisTurn/Turns aura grants without notifying any card (no InvokeEnergyCostChanged/StarCostChanged), and the end-of-turn refresh in CardEditorMod only covers CardCostsLess/CardStarCostsLess kinds, not CardType auras. Additionally NotifyOwnerCardCostsChanged (used on aura apply and on use-limit decrement) only calls InvokeEnergyCostChanged, never StarCostChanged, so CardTypeStarCostsLess auras don't refresh star labels.
SCENARIO: 'Your Attacks cost 1 less this turn' is active and an attack is Retained. After the turn ends, the retained card keeps displaying the discounted energy cost (the real spend would be full price â€” display vs spend mismatch) until some other event refreshes it. A 'Attacks' star-cost aura similarly applies/expires without the star gem number updating.
EVIDENCE: Mod: CardEditorCardTypeCostAuras.cs:46-94 (expiry loop, no notify), 399-416 (NotifyOwnerCardCostsChanged â†’ InvokeEnergyCostChanged only), CardEditorMod.cs:3184-3187 + CardEditorExtraEffects.cs:31830-31863 (refresh only matches CardCostsLess/CardStarCostsLess kinds). Vanilla: CardModel.cs:1306-1319 (cleanup fires EnergyCostChanged/StarCostChanged), NCard.cs:561-562 (star label driven by star cost reads/events).

## [minor] Permanent over-reduction floors base cost at -1 (no-cost sentinel) instead of 0, making the card immune to all future cost modifiers
VANILLA: Permanent in-combat base-cost changes clamp at 0: CardEnergyCost.UpgradeBy uses Math.Max(_base + addend, 0). A 0-base card still shows '0' and still receives later modifiers (e.g. Tangled +1, Modded/FranticEscape AddThisCombat(+1)). The mod's own deck-snapshot path also clamps at 0.
MOD: ApplyPermanentEnergyCost / ApplyPermanentStarCost compute targetCost = Math.Max(-1, baseCost - amount), so reducing by more than the base sets the base to -1. CardEnergyCost.GetWithModifiers early-returns when _base < 0, skipping ALL local modifiers and the global hook, and the mod's NCard patch hides the energy icon for negative local cost.
SCENARIO: 'Created cards permanently cost 2 less' hits a 1-cost token: its energy orb disappears entirely (looks like a curse/no-cost card) instead of showing 0. If the enemy then applies Tangled (+1 to Attacks) or the card gets a vanilla +1-this-combat effect, the cost stays hidden/0 â€” a vanilla card at 0 would visibly cost 1.
EVIDENCE: Mod: CardEditorCreatedCardsCostPatches.cs:326 and 372 (Math.Max(-1, baseCost - amount)), 335 (SetCustomBaseCost), CardEditorCardCostsLessColorPatches.cs:178-183 (negative local cost hides energy icon). Vanilla: CardEnergyCost.cs:186-199 (UpgradeBy clamps at 0), CardEnergyCost.cs:63-66 (_base < 0 skips all modifiers incl. increases); mod's own clamp-at-0 contrast: CardEditorExtraEffects.cs:8890-8897.

## [minor] Permanent cost reduction doesn't clamp existing absolute cost-set modifiers (Confused/Snecko-style), unlike vanilla base reductions
VANILLA: When a vanilla base-cost reduction lands on a card that has absolute local modifiers (e.g. ConfusedPower's SetThisCombat(rolledCost)), CardEnergyCost.UpgradeBy clamps any absolute modifier whose Amount exceeds the new base down to the new base, so the reduction is always visible. The star path similarly removes temp costs above the new base (CardModel.UpgradeStarCostBy).
MOD: ApplyPermanentEnergyCost calls SetCustomBaseCost directly without the clamping step, so a non-reduceOnly absolute modifier set earlier (Confused roll) keeps overriding the new lower base and the 'permanent discount' has no visible effect.
SCENARIO: Vanilla Confused rerolled a card's cost to 3 for the combat. A mod 'created/linked cards permanently cost 2 less' effect then triggers: base drops 3â†’1 internally, but the card still displays and spends 3. The vanilla equivalent (an upgrade-style base reduction) would drop the Confused cost to 1.
EVIDENCE: Mod: CardEditorCreatedCardsCostPatches.cs:293-337 (ApplyPermanentEnergyCost â†’ SetCustomBaseCost with no local-modifier clamp). Vanilla: CardEnergyCost.cs:179-200 (UpgradeBy clamps absolute LocalCostModifiers above the new base), ConfusedPower.cs:42 (SetThisCombat absolute, not reduceOnly), CardModel.cs:1065-1071 (star equivalent removes temp costs above new base).

### VERDICT [confirmed] Mod cost-increase effects re-charge cards that vanilla 'free' powers make free
CONFIRMED on every point; no compensating mod code exists.

VANILLA SIDE (all cited lines check out):
- Hook.cs:1245-1261: ModifyEnergyCostInCombat runs the early loop (TryModifyEnergyCostInCombat) first, then the late loop (TryModifyEnergyCostInCombatLate), and returns the result unmodified afterwards.
- TangledPower.cs:59-68: cost increase implemented in the EARLY hook (modifiedCost = originalCost + Amount).
- FreeSkillPower.cs:14-42 sets modifiedCost = 0 in the LATE hook for Skills in hand/play; FreeAttackPower.cs:14, FreePowerPower.cs:14, CorruptionPower.cs:16, VoidFormPower.cs:44 and BrilliantScarf.cs:57 all likewise use TryModifyEnergyCostInCombatLate. So in vanilla, "free" always runs after "+cost" and wins.
- CardEnergyCost.cs:80: the actual in-combat cost (paid energy) flows through Hook.ModifyEnergyCostInCombat, so the patched method governs the real spend.
- FreeSkillPower.cs:44-64: BeforeCardPlayed decrements the charge for ANY Skill played from hand/play, regardless of cost actually paid â€” so the counter is consumed even when the mod re-charges the card, exactly as the scenario states.

MOD SIDE (all cited lines check out):
- CardEditorCardCostsLessPatches.cs:10-55: Harmony Postfix on Hook.ModifyEnergyCostInCombat (runs after both vanilla loops). Line 46: __result = Math.Max(0m, __result - combined.Delta). A negative Delta ("costs more") turns a vanilla-freed 0 into 1. The __result < 0 guard at line 23 does not protect, because a freed card's result is 0, not negative. The mod's own ForceFree is applied after the delta (lines 48-51), so only vanilla free powers lose, as claimed.
- Negative deltas are first-class: CardEditorExtraEffects.cs:6086-6091 validates CardCostsLess/CardTypeCostsLess with "amount != 0"; line 32021 has the explicit comment "Signed delta: positive reduces cost, negative increases cost"; line 32110 feeds the raw signed Amount into the delta; CardCostAdjustment.Combine (CardEditorExtraEffects.cs:1282-1287) sums deltas. The editor UI renders "...cost {N} more" descriptions (e.g. CardEditorExtraEffects.cs:20289-20328, 21550-21590), so players can genuinely author this effect.
- The display path agrees with the spend path: CardEditorCardCostsLessColorPatches.cs:94-141 postfixes CardCostHelper.TryModifyEnergyCostWithHooks with the same after-late-hooks application; the early-return at line 120 only fires for POSITIVE deltas on already-free cards, so a negative delta bumps the displayed cost too. The card therefore both shows and spends 1.
