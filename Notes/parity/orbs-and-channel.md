# orbs-and-channel
## Orb machinery parity audit (mod card_editor vs vanilla StS2)

Compared the mod's orb effects in `CardEditorExtraEffects.cs` (ExecuteEffectCore cases ~27278-27454, helpers ChannelOrb/ExecuteOrbAction/SelectOrb/EvokeOrb/TriggerOrbPassive/RemoveOrb/ExecuteOrbActionAll ~27576-27768, count-condition helpers ~32691-33788) against vanilla `Core\Commands\OrbCmd.cs`, `Core\Entities\Orbs\OrbQueue.cs`, `Core\Models\OrbModel.cs` + the five orb models, `Core\Hooks\Hook.cs`, and the UI layout in `Core\Nodes\Orbs\NOrbManager.cs`.

**Verified-good (not reported):** all Channel paths (ChannelLightning/Frost/Dark/Plasma/Glass/Random, OrbAction.Channel, ChannelSameType follow-up) delegate to vanilla `OrbCmd.Channel`, so slots-full-evokes-oldest-first, the 1-free-slot grant for non-Defect characters, `History.OrbChanneled`, channel SFX, and `Hook.AfterOrbChanneled` (Metronome etc.) all behave exactly like vanilla; ChannelRandomOrb uses the same `OrbModel.GetRandomOrb(Rng.CombatOrbGeneration)` stream as vanilla Chaos. Focus is applied identically because the mod always calls `orb.Evoke()`/`OrbCmd.Passive()` and the orbs compute `ModifyOrbValue` themselves. Dark `_evokeVal` accumulation and Glass `_passiveVal` decay are preserved (per-instance state, mod never clones live orbs except the explicitly-worded "Channel the same Orb type" follow-up, which channels a fresh orb as its text says). Slot clamps (max 10, min 0, newest-orbs destroyed on slot loss) are delegated to vanilla `OrbCmd.AddSlots/RemoveSlots`. Evoke-all iterates queue head first, matching vanilla `EvokeNext` order, and the mod's custom evoke fires `Hook.AfterOrbEvoked` so ThunderPower-style reactions trigger. TriggerPassive nullifies the target for non-Lightning orbs, matching the vanilla orbs that throw on a non-null target (Dark/Frost/Plasma) and TeslaCoil's Lightning-only targeting.

**Important layout fact established:** in StS2 the orb queue head (`Orbs[0]`, oldest, next to evoke) renders RIGHTMOST on screen (NOrbManager.TweenLayout places index 0 at +x; controller nav sets FocusNeighborRight = index i-1; no horizontal flip on player creature nodes). The mod's action-side `SelectOrb` maps Rightmostâ†’index 0 correctly â€” but its condition-side `GetOrbInPosition` maps the opposite way, which is the one major finding.

## [major] OrbInPosition condition reads leftmost/rightmost inverted (and opposite to the mod's own orb actions)
VANILLA: The orb at OrbQueue.Orbs[0] (oldest, next to evoke) is the RIGHTMOST orb on screen: NOrbManager.TweenLayout positions _orbs[0] at +x (angle -150 deg => x=+0.866r) and UpdateControllerNavigation sets FocusNeighborRight of orb i to orb i-1 (lower index = further right); the next-to-evoke highlight (OrbEvokeType.Front) is _orbs.FirstOrDefault(). The mod's own action selector SelectOrb agrees: Rightmost => matchingOrbs[0], Leftmost (default) => last.
MOD: GetOrbInPosition, used by the 'OrbInPosition' count/condition ("your leftmost orb is Frost" / "your leftmost orb slot is occupied"), maps it backwards: Rightmost => orbs[orbs.Count-1] (newest = visually LEFTMOST) and Leftmost (default) => orbs[0] (oldest = visually RIGHTMOST). So the condition checks the opposite end of the orb row from what its card text and the rest of the mod's orb actions mean.
SCENARIO: Channel Lightning, then Frost (screen shows Lightning on the right, Frost on the left). A card reading "If your leftmost orb is Frost: Evoke your leftmost Orb" fails its condition (GetOrbInPosition returns the Lightning at Orbs[0]) even though the action half of the same card would correctly evoke the Frost. Conversely "if your rightmost orb is Lightning" never matches while Lightning sits visibly rightmost.
EVIDENCE: Mod: CardEditorExtraEffects.cs:33782-33787 (GetOrbInPosition Rightmost=>orbs[Count-1], default/Leftmost=>orbs[0]), inconsistent with mod's own SelectOrb at 27646-27651 (Rightmost=>matchingOrbs[0]); used at 32723-32730, card text at 17173-17186. Vanilla: NOrbManager.cs:217-223 (TweenLayout: i=0 at +x/right), NOrbManager.cs:180-199 (FocusNeighborRight = orb i-1), OrbCmd.cs:71-81 (EvokeNext = Orbs.First(), i.e. the screen-right orb is 'next').

## [minor] Multi-evoke evokes N different orbs instead of vanilla's evoke-same-orb-N-times (no evoke-without-removal)
VANILLA: Every vanilla multi-evoke effect evokes the SAME next orb repeatedly and only dequeues it on the final evoke: Dualcast calls EvokeNext(dequeue:false) then EvokeNext(); Shatter does the same; MultiCast/Quadcast call EvokeNext(..., i == evokeCount-1). A lone orb is therefore evoked X times for X-fold value (Dark's accumulated value dealt twice, etc.).
MOD: The EvokeOrbs effect loops OrbCmd.EvokeNext(choiceContext, owner) with the default dequeue:true each iteration, and OrbAction.Evoke (ExecuteOrbAction/EvokeOrb) always removes the orb before re-selecting. There is no evoke-without-removal anywhere, so amount>1 always consumes N distinct orbs.
SCENARIO: Player has a single Dark orb accumulated to 30. Vanilla Dualcast deals 30 + 30 = 60 to the weakest enemy. A mod-built card with EvokeOrbs amount 2 ("Evoke 2 Orbs.") deals 30 once and the second iteration no-ops on the now-empty queue. With [Dark(30), Frost] channeled, vanilla Multicast x2 deals 60 Dark damage keeping Frost; the mod evokes Dark once then the Frost. Users cannot recreate Dualcast/Multicast/Quadcast/Shatter behavior, and editing such a card through the editor changes its in-game behavior. (Mitigating: the mod's generated text "Evoke {X} Orbs." does describe what it actually does.)
EVIDENCE: Vanilla: Dualcast.cs:26-28, MultiCast.cs:29, Quadcast.cs:30, Shatter.cs:33-34, OrbCmd.cs:71-81 + 95-123 (dequeue parameter). Mod: CardEditorExtraEffects.cs:27389-27395 (EvokeOrbs loop, dequeue defaulted true), 27667-27686 (EvokeOrb unconditionally removes), 19796-19804 (FormatEvokeOrbs text).

## [minor] Custom evoke path fires AfterOrbEvoked without vanilla's null-combat-state guard and with the orb already popped off the choice context
VANILLA: OrbCmd.Evoke only fires Hook.AfterOrbEvoked when player.Creature.CombatState != null (skips reactive powers silently otherwise), and during the hook the evoked orb is still pushed on the PlayerChoiceContext model stack via EvokeNext/EvokeLast's outer PushModel, so any choices/VFX made by AfterOrbEvoked listeners are attributed to the orb.
MOD: The mod's EvokeOrb (used by OrbAction Evoke, single and All-scope) calls Hook.AfterOrbEvoked unconditionally with player.Creature.GetConcreteCombatState(), which can be null; Hook.IterateCombatHookListeners dereferences the combatState when combat is not over/ending, so a null state throws NullReferenceException where vanilla silently skips. It also pops the orb from the choice context before the hook, so listener-made choices attribute to the underlying card instead of the orb.
SCENARIO: Co-op edge case: a mod power/effect evokes orbs for a player whose creature's combat state has been cleared while the fight continues (the situation vanilla's explicit null-check defends against, e.g. the player being removed/downed as the effect resolves). Vanilla machinery skips orb-reactive powers and continues; the mod path crashes with an unhandled NullReferenceException inside the hook iteration.
EVIDENCE: Vanilla: OrbCmd.cs:115-122 (null-guarded hook + RemoveInternal), OrbCmd.cs:76-79 (outer PushModel during hook), Hook.cs:28-38 + 647-654 (IterateCombatHookListeners dereferences combatState when combat not over). Mod: CardEditorExtraEffects.cs:27681-27685 (PopModel before hook; GetConcreteCombatState passed unguarded), CardEditorCombatStateCompat.cs:30-62 (GetConcreteCombatState returns null on failure).
